# Research artifact template

> **What this is**: a documentation of the 5-layer artifact structure used by `/home/a/letter-valence-research/`, written so a future researcher (human or LLM agent) can apply the same structure to a new project without any prior context.
>
> **Validated**: 2026-08-05 on the letter-valence-research project (68 letter-derived features, 0.7377 CV accuracy, 53 files, 15.7 MB, fully reproducible end-to-end).
>
> **For LLM agents**: if you are about to package a research project for public release, read this top to bottom. The 5-layer structure, the 10 mandatory files, and the 18-item checklist will catch the most common omissions.

---

## 1. The 5-layer structure

Every research project artifact should have these 5 layers, in this order from top to bottom. Each layer has a clear purpose and a minimal set of files.

```
my-research-project/
│
├── 0. ENTRY POINTS         (the reader's first 30 seconds)
│   ├── README.md               (headline + layout + reproduction)
│   ├── results/SUMMARY.md      (one-page plain-English summary)
│   ├── arxiv_paper.pdf         (compiled paper, ~10 pages, ~600 KB)
│   └── figures/*.png           (5-10 publication-quality PNGs)
│
├── 1. NARRATIVE             (the prose)
│   ├── blog_post.md            (1,500-2,500 word narrative)
│   ├── linkedin_post.md        (short-form + metadata)
│   ├── research_report.md      (full formal report, 15-25 pages)
│   ├── lit_digest.md           (per-paper digest of foundational works)
│   ├── arxiv_paper.tex         (LaTeX source)
│   ├── METHODOLOGY.md          (detailed reproduction guide)
│   ├── CHANGELOG.md            (version history, semantic versioning)
│   ├── CONTRIBUTING.md         (how to contribute)
│   ├── AUTHORS                 (contributor list)
│   ├── LICENSE                 (dual: MIT for code, CC-BY-4.0 for prose)
│   ├── CITATION.cff            (GitHub's "Cite this repository" feature)
│   └── requirements.txt        (Python dependencies)
│
├── 2. CODE                 (the reproducible part)
│   ├── src/
│   │   ├── __init__.py
│   │   ├── features.py         (or extractors.py — the reusable engine)
│   │   ├── data.py             (loaders + derivation)
│   │   ├── train.py            (model training)
│   │   ├── evaluate.py         (CV, permutation, ablation, learning curve)
│   │   ├── analyze.py          (main entry point)
│   │   └── figures.py          (figure generation)
│   ├── tests/
│   │   ├── README.md
│   │   ├── test_features.py    (or test_extractors.py)
│   │   └── test_*.py
│   └── notebooks/
│       ├── 01_reproduce_main_result.ipynb           (source)
│       └── 01_reproduce_main_result_executed.ipynb   (run with outputs)
│
├── 3. DATA                 (the inputs)
│   ├── README.md               (provenance, citations, license for each file)
│   ├── download.sh             (reproducible fetch script)
│   ├── *.csv, *.json, *.txt    (the actual data, or generated by download.sh)
│
├── 4. RESULTS               (the outputs of the analysis)
│   ├── cv_*.csv                (cross-validation results)
│   ├── learning_curve.csv
│   ├── family_ablation.csv
│   ├── single_family.csv
│   ├── permutation_test.json
│   ├── summary.json            (machine-readable headline numbers)
│   └── word_level_correlations.csv
│
└── 5. FIGURES               (the visual outputs)
    ├── headline_summary.png
    ├── method_comparison.png
    ├── family_ablation.png
    ├── single_family.png
    ├── learning_curve.png
    ├── roc_curve.png
    ├── word_level_correlations.png
    └── feature_heatmap.png
```

## 2. The 10 mandatory files

If a research project does not have these 10 files, it is not ready to share:

| # | File | Why it's mandatory |
|---|---|---|
| 1 | `README.md` | First thing the reader sees. Must have headline number in the first paragraph. |
| 2 | `LICENSE` | Without it, the code is copyrighted by default and unusable. |
| 3 | `requirements.txt` | Without it, the reader cannot reproduce. |
| 4 | `data/README.md` | Documents where each dataset came from and its license. |
| 5 | `src/extractors.py` (or `features.py`) | The reusable engine. The thing future work will copy. |
| 6 | `src/evaluate.py` | The principled evaluation (CV + permutation test + ablation + learning curve). |
| 7 | `src/analyze.py` | One-command reproduction: `python -m src.analyze`. |
| 8 | `tests/test_extractors.py` | At least 30 unit tests with hand-computed expected values, all passing in <2s. |
| 9 | `results/SUMMARY.md` | One-page plain-English summary of every number. |
| 10 | `figures/headline_summary.png` | The single figure that tells the story. |

## 3. The 6 recommended files

These are not strictly required but dramatically increase the credibility and reach of the project:

| # | File | Why it helps |
|---|---|---|
| 1 | `blog_post.md` | Long-form narrative for general audience. Drives traffic. |
| 2 | `linkedin_post.md` | Short-form for LinkedIn algorithm. |
| 3 | `arxiv_paper.tex` + `arxiv_paper.pdf` | Citable academic record. |
| 4 | `CHANGELOG.md` | Version history, semantic versioning. |
| 5 | `CITATION.cff` | GitHub's "Cite this repository" feature. |
| 6 | `notebooks/01_reproduce_main_result.ipynb` | Interactive walkthrough. |

---

## 4. The 4 anti-patterns (what NOT to do)

| Anti-pattern | Why it's wrong | What to do instead |
|---|---|---|
| 1. Single monolithic `main.py` | Impossible to test, reuse, or extend. | Split into `data`, `extractors`, `train`, `evaluate`, `analyze`, `figures`. |
| 2. Code that requires the user to edit paths | Breaks the moment they have a different setup. | All paths via `pathlib.Path(__file__).resolve().parent.parent`. |
| 3. Results files checked in but not in CSV | Future readers cannot load them in pandas. | Every results file is a CSV or JSON. Always. |
| 4. "See the paper for details" | The paper is a separate artifact. Code and paper must be self-contained. | Each layer is documented in its own .md file. |

## 5. The principled evaluation checklist

A serious research project must answer these 6 questions. Each answer must be a single number in `results/SUMMARY.md`:

1. **What is the headline metric?** (e.g. "0.7377 ± 0.0058 5-fold CV accuracy")
2. **Is the signal real?** (permutation test p-value)
3. **What is the upper bound from data?** (learning curve plateau)
4. **What is the upper bound from features?** (family ablation)
5. **What is the strongest single feature family?** (single-family evaluation)
6. **How does it compare to baselines?** (class-prior, stratified random, lexicon, transformer)

If you cannot answer any of these 6 with a number, the analysis is incomplete.

## 6. The 8 figures standard

A research project of moderate scope should produce 8 figures. Each has a known purpose and is reproducible by `python -m src.figures`:

1. `headline_summary.png` — bar chart of methods + null distribution
2. `method_comparison.png` — all methods sorted by accuracy
3. `family_ablation.png` — leave-one-family-out bars
4. `single_family.png` — each family alone, sorted
5. `learning_curve.png` — accuracy vs training set size
6. `roc_curve.png` — ROC for the primary classifier
7. `word_level_correlations.png` — top features by correlation with target
8. `feature_heatmap.png` — features × target quartile heatmap

**Style standard for all figures**:
- 300 dpi
- 200-400 KB per file
- 5-12 inch width
- ColorBrewer palette (no rainbow)
- No top/right spines
- 0.3-alpha dashed gridlines
- Black border on bars (linewidth 0.5)
- Value labels next to each bar

## 7. The reproduction contract

A user landing on the repo should be able to reproduce the headline result with these 4 commands:

```bash
git clone <url>
cd my-research-project
pip install -r requirements.txt
python data/download.sh && python -m src.analyze && python -m src.figures
```

Total time: 5-15 minutes for a project of moderate scope.

If your project cannot be reproduced in 4 commands, the structure is wrong.

---

## 8. License pattern

Use a **dual licence**:
- **MIT** for code (src/, tests/, data/download.sh, any *.py files)
- **CC-BY-4.0** for prose, figures, and documentation (README.md, blog_post.md, research_report.md, lit_digest.md, arxiv_paper.tex, figures/*.png, all .md files)

Write a single `LICENSE` file at the repo root that declares both.

The data files themselves have their own licenses. Document each one in `data/README.md`.

## 9. The 18-item readiness checklist

Run through this list before publishing. **If any item is unchecked, the project is not ready to share.**

- [ ] `README.md` has the headline number in the first paragraph
- [ ] `LICENSE` is present and dual (MIT for code, CC-BY-4.0 for prose)
- [ ] `requirements.txt` has the dependency versions
- [ ] `data/README.md` documents every dataset with citation and license
- [ ] `data/download.sh` works from a clean clone
- [ ] `src/analyze.py` runs end-to-end in <15 minutes
- [ ] `src/figures.py` regenerates all 8 figures
- [ ] `tests/` has at least 30 unit tests, all passing in <2 seconds
- [ ] `notebooks/01_reproduce_main_result.ipynb` executes end-to-end
- [ ] `results/SUMMARY.md` has all 6 required numbers
- [ ] `figures/` has all 8 required figures
- [ ] `arxiv_paper.pdf` compiles to a ~10-page PDF
- [ ] `blog_post.md` is 1,500-2,500 words
- [ ] `CHANGELOG.md` is at version 1.0.0
- [ ] `CITATION.cff` has at least 3 references
- [ ] `.gitignore` excludes LaTeX build artifacts, Python cache, OS junk
- [ ] `AUTHORS` has the contributor list
- [ ] One full clean reproduction was run from scratch and the numbers match

## 10. The 8 lessons from the letter-valence project

These are specific things I got wrong the first time and would do differently next time. They apply broadly to research projects, not just this one.

1. **Don't start with the most popular feature family.** I went in expecting gematria to work; the data said no. Start with the most general test of the hypothesis, not the most specific.

2. **5-fold CV is the right default.** Held-out test is over-rated for projects of moderate size. CV with permutation test is more honest.

3. **At least 30 unit tests, run in <2 seconds.** Anything less feels like the code is untested. Anything more is overkill for a research repo.

4. **The 8 figures standard is non-negotiable.** Each figure answers one specific question. Resist the urge to add a 9th figure unless it answers a question the other 8 don't.

5. **Honest negative results in the README.** "X didn't work" is more useful than "X worked and we tried Y other things that we'll mention briefly". The reader respects you for the former.

6. **The blog post is the most-read artifact.** More people will read the blog than the paper, the notebook, or the code. Spend the most time there.

7. **LaTeX is for the paper. Markdown is for everything else.** `arxiv_paper.tex` + `arxiv_paper.pdf` (compiled). Everything else in `.md`. No exceptions.

8. **The reproduction script is the contract.** `python -m src.analyze` must produce the headline number exactly. If it doesn't, the structure is broken.

## 11. Applying this template to a new project

To apply this template to a new research project, in order:

1. **Create the 5-layer directory structure** (`mkdir -p src tests data results figures notebooks`).
2. **Write the 10 mandatory files first**, in this order: `LICENSE`, `requirements.txt`, `data/README.md`, `src/extractors.py`, `src/evaluate.py`, `src/analyze.py`, `tests/test_extractors.py`, `results/SUMMARY.md`, `figures/headline_summary.png`, `README.md`.
3. **Run a small end-to-end test** of the analysis pipeline before adding more features.
4. **Add the 6 recommended files** once the analysis is stable.
5. **Run through the 18-item readiness checklist** before publishing.

If you find yourself adding files that don't fit any of the 16 categories above, ask: is this really a research artifact, or is it project-specific? If project-specific, it should probably go in a `docs/` or `experiments/` subfolder, not at the top level.
